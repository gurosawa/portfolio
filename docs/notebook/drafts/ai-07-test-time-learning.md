# 더 오래 생각하기와, 풀면서 배우기의 차이

> 이전 분할 초안. 현재 원고는 [추론 시스템 통합 원고](../manuscripts/03-compute-and-orchestration.md)다. 아래 내용은 편집 이력으로 보존하며 별도 발행하지 않는다.

편집 상태: 본문 초안 · 미발행 · AI-07 · 2026-09-10

예정 분류: AI / 개념 설명. 예정 형식: 본문과 고정 모델·갱신 모델의 비교 도식. 실제 추론·코드 실행·모델 학습을 수행하지 않았다.

## 본문 초안

### 시도할 시간이 더 생겼다면

어려운 문제를 모델에게 맡겼는데 첫 답이 만족스럽지 않다. 시간을 더 줄 수 있다면 무엇을 시킬까?

응답을 여러 개 생성해 좋은 답을 고를 수 있다. 먼저 나온 답과 평가 결과를 다시 입력해 개선안을 만들 수도 있다. 한 단계 더 나아가 시도에서 얻은 결과로 모델의 파라미터를 갱신할 수도 있다.

셋 다 같은 문제에 추가 계산을 쓰지만 바꾸는 대상은 다르다. 후보의 수가 늘어나는지, 다음 프롬프트가 달라지는지, 모델이 갱신되는지를 구분하면 ‘더 오래 생각한다’는 말이 조금 더 구체적이 된다.

### 같은 모델로 여러 답을 고르기

가상의 정렬 프로그램을 개선하는 상황을 생각해 보자. 이 글에서는 실제 코드를 생성하거나 실행하지 않는다. 모델이 제안한 후보를 실행 환경에서 검사할 수 있다고 가정하고 절차만 비교한다.

가장 단순한 방식은 같은 모델에서 여러 후보를 얻고 평가한 뒤 가장 좋은 것을 선택하는 것이다. 이때 후보가 늘어나도 모델의 가중치는 그대로다. 처음에는 나오지 않았던 답을 나중에 찾을 수 있지만, 그것만으로 모델이 학습됐다고 말할 수는 없다.

이 비교는 앞 글의 pass@k와도 이어진다. 여러 후보 안에 좋은 답이 있을 가능성과 그 답을 실제로 골라낼 수 있는지는 구분해야 한다. 우리 프로그램 예제에서는 정렬 결과의 정확성과 실행 시간을 검사할 평가 환경이 필요하다.

### 이전 후보를 다음 입력에 넣기

다음 방식은 이전 후보와 실패 이유를 프롬프트에 넣어 새 후보를 만드는 것이다. 예를 들어 ‘중복값이 있는 입력에서 정렬 결과가 틀렸다’는 평가를 돌려준다. 모델은 그 정보를 문맥으로 사용해 수정안을 생성한다.

실패한 후보를 기억하고 더 좋은 후보를 재사용하는 탐색 절차를 만들 수도 있다. 앞선 시도의 정보가 다음 결과에 영향을 주지만, 그 영향은 우선 입력과 외부 기록을 통해 전달된다. 기록이 쌓인다는 사실과 학습 파라미터가 갱신된다는 사실은 같지 않다.

### 시도에서 학습 신호를 얻기

TTT-Discover는 하나의 어려운 문제를 푸는 동안 강화학습을 계속하는 접근이다. 좋은 후보를 재사용하는 탐색과 모델 갱신을 결합하며, 평균적인 응답의 보상뿐 아니라 뛰어난 해 하나를 찾는 목적에 맞춘 학습 목표를 사용한다. 연구는 수학, 커널 엔지니어링, 알고리즘, 생물학의 평가 가능한 과제를 다룬다. [TTT-Discover v2, §2–3](https://arxiv.org/html/2601.16175v2)

우리 예제에 빗대면 후보를 만들고, 검사하고, 그 결과를 다음 학습 갱신에 사용하는 고리가 추가되는 것이다. 실제 TTT-Discover의 재현 실험이라는 뜻은 아니다. 실행 화면에 θ₀와 θ₁을 표시한다면 서로 다른 모델 상태를 설명하기 위한 기호이며, 이미 저장된 체크포인트 파일이 있는 것처럼 표시하지 않는다.

| 비교                            | 반복 생성과 선택 | 결과를 되먹이는 탐색    | 문제를 풀면서 학습               |
| ------------------------------- | ---------------- | ----------------------- | -------------------------------- |
| 추가로 생기는 것                | 응답 후보        | 후보와 평가 이력        | 후보·평가 이력·갱신된 모델 상태  |
| 다음 시도에서 달라질 수 있는 것 | 샘플링 결과      | 프롬프트·출발 후보      | 프롬프트·출발 후보·학습 파라미터 |
| 모델 가중치 갱신                | 없음             | 이 표의 탐색에서는 없음 | 있음                             |
| 평가 결과의 사용처              | 최종 선택        | 다음 탐색 방향          | 탐색과 학습 신호                 |

실제 시스템은 이 방식을 조합할 수 있다. 표는 차이를 설명하기 위한 대표 구성이다. 모든 test-time training이 이 논문과 같은 강화학습이나 같은 목표를 사용한다는 뜻도 아니다.

### 평가기가 학습 방향을 정한다

가상의 정렬 프로그램이 아주 빠른 답을 냈지만 숫자 하나를 빠뜨렸다고 하자. 속도만 보상하면 원하는 프로그램과 다른 후보가 높은 점수를 받을 수 있다. 먼저 결과가 유효한지 검사하고, 그 조건을 통과한 후보에서 성능을 비교해야 한다.

검사를 통과해도 측정 환경이 흔들리면 다음 판단이 달라질 수 있다. 같은 입력과 실행 조건에서 비교하는지, 다른 프로세스가 자원을 사용하고 있지는 않은지, 특정 예제에만 유리한 방법인지를 확인해야 한다. 이것은 이 글의 실험 설계 제안이며 실제 벤치마크 결과는 아니다.

평가를 반복해 본 후보가 많아질수록 평가 환경 자체에 맞춘 답을 고를 가능성도 생각해야 한다. 실제 재현을 설계한다면 개발 중 참고할 평가와 마지막 확인에 쓸 조건을 구분하고, 검사 코드와 변경 내역도 함께 남기겠다.

### 논문의 계산 예산을 읽는 방법

논문 v2의 기본 구현은 Tinker에서 gpt-oss-120b와 rank 32 LoRA를 사용한다. 학습은 50스텝, 스텝마다 512개의 rollout을 생성하며, 단순히 곱하면 25,600개다. 평균 입력 3,000토큰과 생성 16,000토큰을 가정한 해당 실행의 비용을 약 500달러로 설명한다. [TTT-Discover v2, §3.3](https://arxiv.org/html/2601.16175v2)

이 숫자는 당시 논문의 실행 조건이다. 지금의 서비스 가격표나 온프레미스 구축 비용으로 옮길 수 없다. 또한 같은 수의 후보를 생성하도록 맞춘 비교가 총 실행 시간이나 학습 연산량까지 모두 같다는 뜻은 아니다.

자체 환경으로 옮기는 계획이라면 모델을 올릴 수 있는지뿐 아니라 응답 생성, 평가 코드 실행, 학습 갱신에 필요한 자원과 시간을 각각 확인해야 한다. 여기서는 GPU 수나 메모리 사용량을 측정하지 않았으므로 가능 장비나 완료 시간을 제시하지 않는다.

### 무엇을 결과물로 남길 것인가

탐색의 목적이 프로그램 한 개를 찾는 것이었다면 최종 결과물은 검증한 프로그램일 수 있다. 중간에 모델을 갱신했더라도 그 모델이 다른 문제에서도 좋아졌는지는 별도 질문이다.

나는 이런 실험을 기록할 때 최종 후보, 검증 조건, 사용한 모델 상태, 시도·학습 예산을 나누어 남기겠다. ‘좋은 답을 찾았다’와 ‘모델이 일반적으로 좋아졌다’를 같은 결과로 묶지 않기 위해서다.

처음 질문으로 돌아가자. 시간을 더 쓰겠다는 결정 뒤에는 무엇을 바꿀지에 대한 결정이 따라온다. 후보를 더 만들지, 다음 탐색의 입력을 바꿀지, 모델을 갱신할지. 그 선택과 평가 방법이 있어야 추가 계산이 어떤 역할을 했는지 설명할 수 있다.

- 비교 애니메이션을 넣더라도 오른쪽 학습 모델의 점수가 반드시 올라가는 장면을 만들지 않는다. 상태 변화와 성능 향상을 분리한다.
