# 정답률이 올랐는데, 풀 수 있는 문제는 줄었다?

편집 상태: 본문 초안 · 미발행 · AI-01 · 2026-09-10

예정 분류: AI / 개념 설명. 예정 형식: 스크롤 서사와 조작 가능한 평가 예제. 논문 재현 실험은 수행하지 않았다.

## 본문 초안

### 같은 모델을 놓고 다른 결론을 내리는 이유

모델을 바꿨더니 한 번에 맞히는 문제가 늘었다. 그런데 응답을 여러 개씩 모아 평가하자 이전 모델이 더 많은 종류의 문제를 풀었다. 어느 쪽 평가가 잘못된 걸까?

먼저 물어야 할 것은 모델에게 몇 번의 기회를 줬는지다. 그다음은 여러 답 중에서 누가 최종 답을 고르는지다. 이 두 조건을 생략하면 같은 점수를 보고도 서로 다른 서비스를 상상하게 된다.

`pass@k`는 한 문제에 대해 생성한 k개의 응답 중 정답이 하나라도 포함되는지를 본다. 문제별 결과를 평균해 데이터셋 전체의 점수를 계산한다. k가 1이면 한 번 생성한 응답의 성공 정도를 보고, k가 커지면 여러 번 시도해서 해결할 수 있는 문제의 범위를 본다. [RLVR 평가 연구 §2.2](https://arxiv.org/html/2504.13837v5)

이제 실제 모델에서 잠시 떨어져, 손으로 계산할 수 있는 작은 예를 보자.

### 네 문제를 푸는 두 가상의 모델

모델 A와 B에게 똑같은 네 문제를 준다고 하자. 각 문제를 한 번 생성해 맞힐 확률은 아래처럼 정했다. **설명을 위해 만든 확률이며 실제 모델을 측정한 값은 아니다.**

| 문제   | 모델 A | 모델 B |
| ------ | -----: | -----: |
| 문제 1 |    90% |    25% |
| 문제 2 |    90% |    25% |
| 문제 3 |     0% |    25% |
| 문제 4 |     0% |    25% |

A는 두 문제에서 정답을 자주 내놓는다. 나머지 두 문제에서는 정답을 생성하지 못하도록 가정했다. B는 어느 문제도 자주 맞히지 못하지만, 네 문제 모두에서 정답을 낼 가능성이 있다.

한 번씩 생성했을 때 평균 성공 확률은 A가 45%, B가 25%다. 사용자에게 바로 답 한 개를 주는 상황만 보면 A 쪽 결과가 좋다.

반복 생성은 어떨까? 여기서는 각 시도가 같은 확률을 유지하며 서로 독립이라고 가정한다. 한 문제를 맞힐 확률이 p라면, k번 모두 틀릴 확률은 `(1-p)^k`다. 따라서 한 번 이상 맞힐 확률은 `1-(1-p)^k`가 된다. 이 값을 문제마다 구한 뒤 평균한다.

| 문제당 시도 횟수 k | 모델 A의 기대 pass@k | 모델 B의 기대 pass@k |
| ------------------ | -------------------: | -------------------: |
| 1                  |               45.00% |               25.00% |
| 2                  |               49.50% |               43.75% |
| 4                  |               50.00% |               68.36% |
| 8                  |               50.00% |               89.99% |

네 번부터 B가 앞선다. A에 기회를 더 줘도 문제 3과 4는 이 가정 안에서 풀리지 않는다. B는 시도가 쌓이면서 네 문제 모두에서 정답을 발견할 가능성이 커진다. 같은 모델 쌍이지만 질문을 바꾸니 답도 바뀌었다.

표의 A는 실제 학습 후 모델, B는 실제 베이스 모델을 뜻하지 않는다. 또 평균 성공 확률 하나에 공식을 적용한 결과도 아니다. 문제별 성공 확률이 다르므로 각각 계산해야 한다.

### 논문에서는 무엇을 비교했을까

Yue 등의 연구는 여러 모델과 수학·코드·시각 추론 과제에서 RLVR 전후를 비교했다. 작은 k에서는 학습 후 모델이 앞서지만, 큰 k에서는 베이스 모델이 따라잡거나 앞서는 현상을 보고했다. v5의 Table 4에서는 Omni-MATH-Test의 GRPO 학습 150→450스텝 사이 pass@1이 25.1→28.3, pass@256은 68.3→63.9로 바뀐다. 표의 값은 백분율 점수이며 이 실험 조건에 한정된다. [논문 v5, §4.4·Table 4](https://arxiv.org/html/2504.13837v5)

여기서 서로 다른 축을 혼동하면 안 된다. 고정된 모델과 분포에서 k를 늘릴 때 기대 pass@k가 내려가는 것은 아니다. 위 논문 표는 **학습 단계가 바뀐 모델들**을 동일한 평가 횟수로 비교한 것이다.

이 결과만으로 RL의 가능성 전체를 결론 내릴 수도 없다. ProRL은 장기 학습, KL 제어, 기준 정책 갱신 등을 사용하는 다른 조건에서 추론 범위 확장을 보고했다. 두 연구를 함께 읽으면, 모델 이름이나 학습 방식의 약자만으로 결과를 예상하기 어렵다는 점이 드러난다. [ProRL](https://arxiv.org/abs/2505.24864v1)

### 정답이 들어 있는 묶음과 사용자에게 주는 답

앞의 예에서 B는 여덟 번 시도했을 때 약 90%의 기대 점수를 얻었다. 이제 여덟 개의 답을 사용자 앞에 펼쳐보자. 정답 하나와 그럴듯한 오답 일곱 개가 섞여 있다면 어떤 답을 보여줘야 할까?

`pass@k`를 계산하는 평가자는 정답 여부를 확인할 수 있다고 전제한다. 실제 서비스에는 같은 능력을 가진 선택기가 없을 수 있다. 가장 긴 답을 고르거나, 다른 모델에게 고르게 하거나, 다수결을 쓰는 순간에는 그 선택 과정의 정확도도 평가 대상이 된다. 후보에 정답이 있는 비율과 최종 선택이 맞는 비율을 따로 기록해야 한다. 연구도 pass@k와 best-of-N·다수결의 목적을 구분한다. [RLVR 평가 연구 §2.2](https://arxiv.org/html/2504.13837v5)

코드라면 일부 요구사항을 테스트로 확인할 수 있다. 하지만 테스트가 놓친 조건까지 코드가 만족하는지는 별개다. 문서 요약이나 원인 분석처럼 정답 판정이 어려운 업무에서는 선택기의 역할을 더 신중하게 정의해야 한다.

비용도 함께 변한다. 여러 후보를 생성하면 생성량이 늘고, 후보를 평가하는 작업도 추가된다. 병렬로 실행해 대기 시간을 줄여도 필요한 전체 작업이 사라지는 것은 아니다. 얼마나 생성하고 무엇을 검사했는지를 기록해야 성능 개선의 대가를 읽을 수 있다.

### 모델을 고르기 전에 적어둘 평가 조건

업무를 평가할 때는 최종 응답 한 개의 성공률을 출발점으로 삼자. 여러 후보를 사용할 계획이라면 후보 생성 수, 선택 방법, 최종 선택 성공률을 추가한다. 모델 버전, 프롬프트, 생성 설정, 토큰 한도, 평가 데이터와 채점 기준도 함께 고정해야 비교가 가능하다.

이번 글의 가상 모델 A와 B 중 무엇을 택할지는 제품에 달렸다. 짧은 시간 안에 답 하나를 내야 하는 업무와, 후보를 여러 개 만든 뒤 실행 검사로 고를 수 있는 업무는 같은 선택을 요구하지 않는다.

다음 벤치마크 표를 읽을 때는 점수 옆의 작은 조건부터 보자. 한 번의 답인가, 여러 후보의 가능성인가. 그중 정답을 골라내는 과정까지 포함한 평가인가. 어떤 모델이 낫다는 판단은 그 뒤에 해도 늦지 않다.
