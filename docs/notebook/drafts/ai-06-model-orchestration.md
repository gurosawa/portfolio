# 모든 질문에 가장 비싼 모델을 써야 할까?

> 이전 분할 초안. 현재 원고는 [추론 시스템 통합 원고](../manuscripts/03-compute-and-orchestration.md)다. 아래 내용은 편집 이력으로 보존하며 별도 발행하지 않는다.

편집 상태: 본문 초안 · 미발행 · AI-06 · 2026-09-10

예정 분류: AI / 개념 설명, OPS·SEC 관련 글 연결. 예정 형식: 스크롤 서사와 준비된 경로 비교. 실제 API 호출·가격 측정·고객 데이터 사용은 하지 않았다.

## 본문 초안

### 요청 하나 안에 여러 일이 들어 있다

다음과 같은 요청이 들어왔다고 하자.

> 지난달 매출이 감소한 원인을 문서와 표를 참고해 설명해줘.

답을 만들기 위해서는 지난달이 언제인지 정하고, 관련 자료를 찾고, 비교할 숫자를 계산하고, 문서의 설명과 수치를 대조해야 한다. 자료가 뒷받침하는 범위에서만 원인을 설명하는 일도 남는다.

이 글에서는 가상의 월별 매출표와 업무 문서를 사용하는 설명용 상황을 만든다. 실제 회사의 매출이나 실제 모델 응답은 아니다. 우리가 따라갈 것은 요청이 각 작업을 거쳐 답이 되는 과정이다.

### 먼저, 지금 부족한 것이 무엇인지

모델에게 관련 자료가 없다면 자료를 찾아야 한다. 표의 합계가 필요하면 계산이 필요하다. 문서의 ‘지난 분기’와 표의 ‘지난달’이 서로 다른 기간이라면 기준을 맞춰야 한다.

이 단계에서 모든 문제를 모델의 추론 능력 부족으로 볼 이유는 없다. 자료가 없는지, 자료는 있지만 계산이 틀린지, 여러 근거의 관계를 판단하지 못하는지에 따라 다음 작업이 달라진다.

설명용 경로는 네 단계로 시작한다. 요청을 정리하고, 문서와 표를 가져오고, 비교 값을 계산한 뒤, 근거를 연결해 응답한다. 각 단계에는 입력과 기대 결과가 있어야 한다. 그래야 실패했을 때 어디로 돌아갈지 정할 수 있다.

### 작은 모델이 일을 나눠 맡긴다면

ToolOrchestra는 모델과 도구를 조율하는 작은 오케스트레이터를 학습하는 연구다. 도구에는 검색과 코드 실행뿐 아니라 전문 모델과 더 큰 범용 모델도 포함된다. 학습 보상은 결과·효율·사용자 선호를 고려한다. [ToolOrchestra v1, §3](https://arxiv.org/html/2511.21689v1)

논문의 HLE 텍스트 하위 집합 비교에서 Orchestrator-8B는 37.1, 기본 도구를 사용하는 GPT-5 비교 구성은 35.1을 기록했다. 이때 8B는 조율하는 모델의 크기다. 시스템은 GPT-5 등의 모델을 도구로 사용할 수 있었다. 8B 모델 하나의 독립적인 능력 비교나 폐쇄망 실험으로 해석해서는 안 된다. [Table 1 및 설명](https://arxiv.org/html/2511.21689v1)

이 연구에서 가져올 설계 질문은 분명하다. 어떤 작업을 누구에게 맡기고, 어떤 결과가 돌아왔을 때 다음 단계로 넘어갈 것인가. 아래 매출 분석 경로는 이 질문을 설명하기 위해 작성한 예이며 논문의 실험을 재현한 것이 아니다.

### 도구를 호출했다고 일이 끝난 것은 아니다

문서 검색 결과가 왔다고 하자. 매출 감소를 설명하는 문장은 있지만 작성일이 두 달 전이다. 여기서 곧장 응답을 작성하면 다른 기간의 설명을 가져다 붙일 수 있다. 검색 조건을 바꿔 다시 찾거나, 해당 기간의 자료가 없다고 밝혀야 한다.

계산 도구가 실패할 수도 있다. 날짜 열을 읽지 못했다면 입력 형식을 고쳐 재시도할 수 있다. 파일을 읽을 권한이 없다면 접근 권한을 확인해야 한다. 두 문제는 모두 ‘도구 실패’지만 다음 행동은 다르다.

이 예제의 정책은 허용된 도구 안에서만 경로를 선택하도록 정한다. 접근 권한이 없는 자료를 다른 모델이나 외부 서비스로 보내 해결하려고 하지 않는다. 재시도 횟수도 제한한다. 같은 실패를 반복하며 답을 기다리는 대신, 어느 자료를 확보하지 못했는지 설명하는 응답으로 끝낼 수 있어야 한다.

### 비용 우선과 품질 우선은 어떻게 달라질까

독자는 같은 요청의 준비된 경로를 세 가지 조건으로 비교할 수 있다. 여기서 우선순위는 예시 경로의 선택 조건이며, 실제 성능을 측정한 정책이 아니다.

| 조건                    | 예시 경로                                              | 확인할 점                                            |
| ----------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 내부 자료와 모델만 허용 | 내부 검색 → 계산 → 내부 모델의 설명                    | 외부 호출 없이 확보한 근거로 무엇까지 말할 수 있는가 |
| 비용 우선               | 검색 → 계산 → 가벼운 모델의 초안 → 필요할 때 추가 검토 | 호출을 줄인 과정에서 검사가 빠지지 않았는가          |
| 품질 우선               | 검색 → 계산 → 추가 근거 대조 → 허용된 강한 모델의 검토 | 추가 검토가 실제 오류를 줄이는가                     |

더 비싼 경로가 더 정확하다는 결과를 미리 넣지는 않는다. 서로 다른 경로가 어떤 작업을 추가하거나 생략하는지 보여주고, 정확도는 별도 평가가 필요하다고 표시한다.

외부 모델을 허용하는 설정도 ‘모든 자료를 외부로 전송해도 된다’는 뜻은 아니다. 실제 서비스에서는 허용된 도구와 전달 가능한 데이터 범위가 정해져 있어야 한다. 이 글의 화면은 그 경계를 조건으로 받아 경로를 설명한다.

### 모델 호출 단가만으로는 비용을 알 수 없다

작은 모델의 호출 단가가 낮아도 같은 일을 여러 번 반복하면 전체 비용이 늘 수 있다. 검색·코드 실행·추가 모델의 호출과 오케스트레이터의 추론도 작업에 포함된다.

실제 실험을 한다면 각 호출의 입력·출력 토큰, 적용한 가격과 날짜, 도구 비용을 기록하고 합산할 수 있다. 자체 서버를 사용한다면 API 가격 대신 서버 사용과 운영 비용을 별도로 계산해야 한다. 이 초안에는 그 값이 없으므로 달러나 원화의 비용을 만들어 넣지 않는다.

대기 시간은 별개의 지표다. 순차로 수행하는 경로와 동시에 처리하는 경로는 시간을 합산하는 방식이 다르다. 화면의 선 길이나 애니메이션 속도를 응답 시간으로 읽게 해서는 안 된다. 초안의 장면은 호출의 순서를 보여줄 뿐이다.

### 평가할 대상은 완성된 응답까지다

경로를 잘게 나눴다고 최종 응답이 좋아졌다고 할 수는 없다. 우리 예제에서는 다음을 따로 확인해야 한다. 같은 기간을 비교했는가. 계산이 맞는가. 문서가 실제로 그 원인을 뒷받침하는가. 근거가 없는 부분을 추측으로 채우지 않았는가.

도구가 모두 성공했어도 이 중 하나에서 실패할 수 있다. 반대로 필요한 자료가 없다고 정확히 알리는 응답은 길고 확신에 찬 분석보다 그 상황에 적절할 수 있다. 따라서 도구 성공 횟수와 업무 성공률을 같은 지표로 쓰지 않는다.

이 글이 다룬 선택은 모델 하나의 순위를 정하는 일이 아니다. 어떤 입력을 어떤 경로로 처리하고, 어디에서 결과를 검사하며, 무엇을 사용자에게 전달할지 결정하는 일이다. 모델·도구·정책·평가를 함께 볼 때 요청 하나의 실제 비용과 품질을 비교할 수 있다.
